Skills are written conventions that load when the work matches them. They put the same guidance in front of the agent on every run, instead of relying on it being remembered.

## Workflow skills

| Skill | When it loads |
|---|---|
| `fairmind-context` | Starting any Fairmind development work — pulls project, session, user story, task plan, requirements, test expectations, and related documents |
| `fairmind-tdd` | Implementing against Fairmind acceptance criteria, with journal traceability |
| `fairmind-code-review` | Reviewing implementation work — plan to journal to code traceability, requirements verification, cross-repository integration checks |

## The gate layer

| Skill | When it loads |
|---|---|
| `fairmind-gate` | Designing a loop-mode stop condition: the five check types, descriptor specification, RED-first authoring, and admission |
| `custom-check-authoring` | A criterion the five built-in types do not cover, needing a custom check and its admission self-test |
| `task-compilation` | Classifying an external ticket's acceptance criteria into check types for `/loop-import`, resolving ambiguity by interview rather than by guessing |

See [Loop mode](/coding/loop-mode) for what these three build.

## Working with the brain

These skills work against the requirements, decisions and history your Fairmind project
already holds, rather than against the repository alone.

| Skill | When it loads |
|---|---|
| `brain-rebuild-requirements` | Recovering the functional and technical requirements of a system that already exists — module by module, from the ingested code and what the project records about it, each draft naming at least one file or function, with what the brain holds about each module reported as conclusions with references and the brain's own coverage sentence |
| `brain-new-requirement` | Turning an idea into a need, user stories and requirements after asking the brain for precedents — including the ones that were removed or replaced, and why when the brain says |
| `brain-add-document` | Filing a document the brain can cite, with a summary the agent writes because this door runs no model; also filing a repository's working artifacts (design notes, reviews, plans) as reference cards that point to the file in git |
| `brain-record-decision` | Recording, when you ask for it, a decision taken in the session, an issue found and left for later, or the replacement of a decision the project already holds — after looking for the same or a competing one, and showing you the draft before anything is sent |
| `brain-onboard` | Starting on a project you do not know: its brief in one call, then the why behind each file you open — or, when asked, writing or regenerating that brief from what the brain holds |
| `brain-impact` | Working out what a change touches before it is made — what the brain holds about the files and directories it lands in, a ticket, a pull request or an idea, as conclusions with references, and what uses the symbols in them |
| `brain-ask` | Asking the brain first when a question is about why the code is the way it is, what was decided, whether an idea was tried before, what speaks against an approach, or what a ticket or pull request established — one well-formed question, then the code, GitHub or the tracker only for what the answer leaves open |
| `brain-extract-components` | Turning a blueprint, from your checkout or a link you give, into the components it names — responsibility, layer, technology, the directories that implement each, and what each belongs to and depends on — when you ask, after showing you the draft |
| `brain-import-pull-requests` | Bringing a repository's merged and closed pull requests into the brain when you ask — each one read with your own `gh` and recorded as a short card with a summary the agent writes — so a read of a file returns the reasons written about it |
| `brain-seed` | Seeding a project's brain when you ask — the documents you name, as links with a summary the agent writes, the tracker tasks of the projects and lists you pick updated in the last 90 days, the whole of any epic you pick, and the merged and closed pull requests of the same window, read through the connections you already have. What it sends is under [What leaves your machine](/coding/data-flow) |

`brain-rebuild-requirements` and `brain-new-requirement` record their output as **proposals**,
and `brain-record-decision` records an issue as a proposal. A person confirms or rejects each
proposal, and reruns converge on the same records rather than duplicating them.
`brain-record-decision` records a decision as **taken**: you stated it where you took it, so it
lands confirmed and changes only by being replaced. `brain-extract-components` works the same way for components: each
lands as a proposal, a rerun over the same blueprint finds the same records by their titles,
and a component with the title of one already recorded is reported for a person to decide
rather than merged.
`brain-add-document` files a document as a proposal too: it waits in the review queue
until a person confirms it. A working artifact kept in the repository takes a different route; what it sends, when, and what follows are in the plugin README under *What leaves your machine*. `brain-onboard` reads by default and writes nothing; asked to write the
brief, it records it as a proposal and shows what changed against the confirmed version.
`brain-import-pull-requests` is different again: its cards are
recorded confirmed, because an import asserts only that a pull request happened, and only a project admin can
remove one person's cards from a project's brain.
`brain-seed` brings the three in together in one run, in that order, after one yes, asked before any document text or comment is collected: tasks and pull requests are recorded confirmed as short cards, and each document lands as a proposal for the review queue.
`brain-impact` records nothing: its answer is a report of conclusions with references, and
`brain-new-requirement` calls it to ground its drafts. It follows the uses of code the platform
has indexed, not the paths a request takes at run time, and its report says so on its first
line. For what each skill sends to the platform, see
[What leaves your machine](/coding/data-flow).

<Note>
They need [connected mode](/coding/connected-mode) — run `/fairmind-connect` once per
checkout first. Standalone there is nothing to read from, so they stop and say so instead of
degrading. They also need a platform release that serves the brain tools; when it does not,
they name the release and stop.
</Note>

## Loading a skill deliberately

Skills load on their own when the work matches the description in the table above — that is the point of writing the description carefully. To force one, name it in the request:

```text
Use the fairmind-gate skill to define the stop condition for this task
```

A skill announces itself when it loads, so you can tell which guidance is in play.
